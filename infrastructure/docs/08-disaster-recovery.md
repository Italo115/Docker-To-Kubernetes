# 08 — Disaster Recovery & Standard Operating Procedures

> **Status:** This document defines the target backup design **and** the recovery
> runbook. As of this writing the cluster has **no backups configured** (no
> `barmanObjectStore` on the CNPG `Cluster`, no VM snapshot export, no Velero).
> Sections 4–6 are the procedures to implement; sections 7–9 are the runbook to
> execute when the data centre is lost. Treat the "Implement" sections as a
> checklist that must be completed before this DR plan is real.

---

## 1. Scope and goals

The platform runs as a **single physical Kubernetes cluster** (OpenStack/Magnum,
Cinder CSI for storage) hosting four namespace tenants — `dev`, `qa`, `uat`,
`prod` — reconciled by Flux from `oci`/Bitbucket. The complete declarative state
lives in two git repos (`infrastructure/`, `helm-charts/`). The only state that
is **not** in git is:

1. **Postgres data** — the CNPG `Cluster` named `postgres` in namespace `postgresql`.
2. **Generated secrets** — per-app DB credentials (`postgres-<component>-app`),
   the CNPG superuser secret (`postgres-superuser`), and image-pull/registry creds.
3. **The SOPS GPG private key** — without it Flux cannot decrypt anything in `secrets/`.
4. **Container images** — stored in the in-cluster Harbor (`harbor.example.com`),
   which itself runs in the cluster (namespace `artifactory`).

This plan covers backing those up to **Azure Blob Storage** (off-site, different
cloud than the OpenStack data centre) and recovering onto a freshly bootstrapped
cluster.

### Recovery objectives

| Metric | Target | Notes |
|---|---|---|
| **RPO** (max data loss) | ≤ 5 min for Postgres | Continuous WAL archiving to Azure gives near-continuous PITR. VM snapshots are daily → ≤ 24 h for non-DB VM state. |
| **RTO** (time to restore) | ≤ 2–4 h for `prod` | Flux re-bootstrap (~30 min) + Postgres restore (size-dependent) + app reconcile (~15 min). |
| **Backup retention** | 30 days PITR, 90 days monthly | Tune `retentionPolicy` and Azure lifecycle rules to budget. |

## 2. What can and cannot be recovered from git alone

| Component | In git? | Recovery source |
|---|---|---|
| Flux config, Kustomizations, HelmReleases | ✅ `clusters/my-cluster`, `apps/`, `infrastructure/` | `flux bootstrap` from Bitbucket |
| App workloads (Deployments, Services, Ingress) | ✅ rendered by chart | Flux reconcile after bootstrap |
| App config (`values.yaml`, `values-patch.yaml`) | ✅ | git |
| SOPS-encrypted secrets (API tokens, OAuth, vault creds) | ✅ `secrets/` (ciphertext) | git **+ GPG key** (§3) |
| **Postgres data** | ❌ | **Azure Blob (CNPG Barman)** — §4 |
| **Generated DB-app passwords** | ❌ (`helm.sh/resource-policy: keep`, cluster-only) | restored with Postgres roles (§4) **or** secret backup (§5) |
| **CNPG superuser secret** | ❌ (operator-generated) | regenerated by operator on fresh cluster |
| **Container images** | ❌ (in-cluster Harbor) | Harbor backup or upstream rebuild — §6 |
| **VM / node OS state** | ❌ | **Azure Blob (VM snapshot export)** — §6 |

> **The single most dangerous gap is the GPG key.** If the data centre is lost
> and the GPG private key was only inside that cluster, every `secrets/` file in
> git becomes undecryptable ciphertext and the platform cannot be rebuilt. Back
> it up first (§3).

## 3. Back up the SOPS GPG key (do this first, today)

The key (fingerprint `<YOUR_GPG_FINGERPRINT>`) is stored in the
cluster as Secret `sops-gpg` in `flux-system`. Export it and store it **off the
cluster**, in at least two independent locations.

```bash
# Export the armored private key from the running cluster
kubectl get secret sops-gpg -n flux-system \
  -o jsonpath='{.data.sops\.asc}' | base64 -d > /tmp/sops-private.asc

# Store it in Azure Key Vault (NOT Blob — Key Vault for secrets)
az keyvault secret set \
  --vault-name <KEYVAULT_NAME> \
  --name sops-gpg-private \
  --file /tmp/sops-private.asc

# Also keep an offline copy (encrypted USB / password manager / printed paper key)
shred -u /tmp/sops-private.asc   # never leave it on disk
```

**Verify** you can re-import it on a clean machine before trusting it:

```bash
az keyvault secret download --vault-name <KEYVAULT_NAME> --name sops-gpg-private --file k.asc
gpg --import k.asc
sops -d secrets/0-base/operations/auth-server.yaml | head   # must decrypt
```

Rotate the off-site copy whenever the key changes (it shouldn't, but if it ever
is rotated, both copies must be updated).

## 4. Postgres backups to Azure Blob (CNPG Barman Cloud)

CNPG streams **base backups + continuous WAL archiving** to an object store via
Barman Cloud. Azure Blob is a first-class target (`azureCredentials`). This gives
**point-in-time recovery (PITR)** with an RPO of one WAL segment.

### 4.1 Provision Azure storage

```bash
az group create -n <RESOURCE_GROUP> -l <AZURE_REGION>
az storage account create -n <STORAGE_ACCOUNT> -g <RESOURCE_GROUP> \
  --sku Standard_GRS --kind StorageV2 --min-tls-version TLS1_2
az storage container create --account-name <STORAGE_ACCOUNT> -n postgres
# Lifecycle: expire blobs after 30 days (PITR window) — tune to retention policy
```

Use **GRS** (geo-redundant) so the backup itself survives an Azure region loss.

### 4.2 Store the storage credential as a SOPS secret

The Azure storage account key is a credential → it goes in `secrets/`, SOPS-encrypted.

```yaml
# secrets/5-infrastructure/azure-backup.yaml  (then: sops -e -i this file)
apiVersion: v1
kind: Secret
metadata:
  name: azure-backup-creds
  namespace: postgresql
type: Opaque
stringData:
  AZURE_STORAGE_ACCOUNT: <STORAGE_ACCOUNT>
  AZURE_STORAGE_KEY: "<account-key>"
```

Wire it into `clusters/my-cluster/secrets-infrastructure.yaml` (applied to `postgresql`
namespace alongside the cluster). Encrypt before commit; the pre-commit hook in
`06-bootstrap.md` blocks plaintext.

### 4.3 Add `barmanObjectStore` to the CNPG Cluster

Edit `infrastructure/configs/pg-cluster.yaml`, add under `spec:`:

```yaml
  backup:
    retentionPolicy: "30d"
    barmanObjectStore:
      destinationPath: "https://<STORAGE_ACCOUNT>.blob.core.windows.net/postgres"
      azureCredentials:
        storageAccount:
          name: azure-backup-creds
          key: AZURE_STORAGE_ACCOUNT
        storageKey:
          name: azure-backup-creds
          key: AZURE_STORAGE_KEY
      wal:
        compression: gzip
        maxParallel: 4
      data:
        compression: gzip
```

> **HA note:** the cluster currently runs `instances: 1` — there is no standby.
> Consider raising to `instances: 3` for local HA so a single node loss is not a
> recovery event at all. DR (this doc) still applies for full-site loss.

### 4.4 Schedule backups

```yaml
# infrastructure/configs/pg-scheduledbackup.yaml  (add to configs/kustomization.yaml)
apiVersion: postgresql.cnpg.io/v1
kind: ScheduledBackup
metadata:
  name: postgres-daily
  namespace: postgresql
spec:
  schedule: "0 0 2 * * *"        # 02:00 daily (6-field CNPG cron: sec min hour ...)
  backupOwnerReference: self
  cluster:
    name: postgres
  method: barmanObjectStore
```

WAL is archived continuously between base backups, so PITR works to any moment in
the retention window, not just the nightly snapshot.

### 4.5 The credentials gotcha (read before a restore)

App DB roles and their passwords are created by each app's `platform`
bootstrap Job, which writes a `postgres-<component>-app` Secret with
`helm.sh/resource-policy: keep`. On a **fresh** cluster that Secret does not
exist yet, so the Job **generates a new random password** — but a Barman restore
brings back the **old** role password baked into the database. The app Secret and
the database role then disagree and every app fails to connect.

Two ways to handle this; pick one and document which you use:

- **(A) Back up the app secrets too (§5)** and restore them *before* apps
  reconcile, so the Job sees an existing Secret and reuses the old password
  (matching the restored role). Simplest; recommended.
- **(B) Reset role passwords post-restore** to whatever the freshly-generated
  Secrets contain:
  ```bash
  kubectl -n app-prod get secret postgres-<comp>-app -o jsonpath='{.data.password}' | base64 -d
  # then, as superuser in the restored DB:
  ALTER ROLE "<comp>-app" WITH PASSWORD '<that-password>';
  ```

## 5. Back up generated secrets

These never enter git/SOPS and are not in the Postgres backup. Snapshot them to
Azure Blob nightly. They are already Kubernetes Secrets, so a small CronJob (or an
external scheduled task with cluster read access) suffices.

```bash
# Per env: dump the keep-policy DB-app secrets + pull secrets, encrypt, upload
for ns in app-dev app-qa app-uat app-prod postgresql; do
  kubectl -n "$ns" get secret -o yaml \
    -l 'app.kubernetes.io/managed-by!=Helm' 2>/dev/null > "/tmp/$ns-secrets.yaml"
  # Encrypt with the same GPG key so the blob is never plaintext
  gpg --encrypt --recipient <YOUR_GPG_FINGERPRINT> \
    --output "/tmp/$ns-secrets.yaml.gpg" "/tmp/$ns-secrets.yaml"
  az storage blob upload --account-name <STORAGE_ACCOUNT> -c secrets \
    -n "$(date +%F)/$ns-secrets.yaml.gpg" -f "/tmp/$ns-secrets.yaml.gpg" --overwrite
  shred -u "/tmp/$ns-secrets.yaml" "/tmp/$ns-secrets.yaml.gpg"
done
```

> The encrypted blob is useless without the GPG key (§3) — which is exactly the
> property we want.

## 6. VM snapshots and Harbor images to Azure Blob

### 6.1 VM snapshots (OpenStack → Azure Blob)

The cluster nodes are OpenStack VMs. Azure Blob cannot snapshot a VM directly, but
it can **store an exported snapshot image**. Daily flow:

```bash
# 1. Snapshot each node VM in OpenStack (quiesced / off-peak)
openstack server image create --name "node-$(date +%F)" <server-id>

# 2. Download the image
openstack image save --file "/tmp/node-$(date +%F).qcow2" <image-id>

# 3. Upload to Azure Blob (azcopy handles large files + resumable transfer)
azcopy copy "/tmp/node-$(date +%F).qcow2" \
  "https://<STORAGE_ACCOUNT>.blob.core.windows.net/vm-snapshots/<SAS>"
```

**Better alternative — Velero.** For Kubernetes-aware DR, run
[Velero](https://velero.io) with its Azure Blob plugin. It backs up cluster API
objects **and** Cinder PV contents (via restic/Kopia file-level backup) directly
to Azure Blob, and restores them onto a new cluster. This is more granular and
faster to restore than raw VM images, and it captures PVs CNPG doesn't (e.g.
Harbor, MinIO, Nexus). VM snapshots remain useful only if you need to recover the
node OS itself rather than just the cluster workloads.

> Recommendation: Velero for cluster/PV state, VM snapshots optional. Raw VM
> images are large and slow; you re-bootstrap the OS from Magnum/cloud-init anyway.

### 6.2 Harbor images

Harbor stores its registry blobs on a Cinder PV inside the cluster. Options:

- Velero backs up the Harbor PVs as part of §6.1.
- Or rely on **rebuild from CI** — every image is reproducible by re-running the
  `helm-charts` and app pipelines, since source lives in Bitbucket. Slower, but
  zero extra storage. For `prod` recovery speed, prefer Velero-backing the Harbor
  PVs so images are immediately present.

## 7. Disaster recovery runbook (full site loss)

Execute in order. Do **not** skip the GPG step — nothing decrypts without it.

### Phase 0 — Provision a new cluster

1. Stand up a fresh Kubernetes cluster (new OpenStack Magnum cluster, or any
   provider). Get a working `KUBECONFIG`.
2. **Label the node pools** exactly as in `06-bootstrap.md §Node pool labels`:
   ```bash
   kubectl label node <infra>     workload=infrastructure
   kubectl label node <postgres>  workload=postgres
   kubectl label node <dev-n>     workload=dev
   kubectl label node <prod-n>    workload=prod
   ```
   Without these labels, `nodeSelector` pinning leaves pods `Pending`.

### Phase 1 — Restore the GPG key

```bash
az keyvault secret download --vault-name <KEYVAULT_NAME> --name sops-gpg-private --file /tmp/k.asc
gpg --import /tmp/k.asc && shred -u /tmp/k.asc
```

### Phase 2 — Bootstrap Flux from Bitbucket

```bash
export KUBECONFIG=~/.kube/my-cluster
flux bootstrap git \
  --url=ssh://git@bitbucket.org/my-org/infrastructure.git \
  --branch=main \
  --path=clusters/my-cluster \
  --components-extra=image-reflector-controller,image-automation-controller \
  --private-key-file=~/.ssh/id_rsa

# Install the SOPS key as the in-cluster secret so Flux can decrypt secrets/
gpg --export-secret-keys --armor <YOUR_GPG_FINGERPRINT> | \
  kubectl create secret generic sops-gpg -n flux-system --from-file=sops.asc=/dev/stdin
```

Flux now reconciles `flux-system → secrets-infrastructure → infrastructure →
infrastructure-configs → secrets-<env> + apps-<env>`. The CNPG operator comes up,
and the `postgres` Cluster will try to **initdb a new empty database** — this is
where we intervene to restore instead.

### Phase 3 — Restore Postgres from Azure (PITR)

Pause the apps that depend on the DB, then recover the cluster from the Barman
store. Temporarily replace the `postgres` Cluster spec with a **recovery
bootstrap** (do this in git on a recovery branch, or apply directly and reconcile
git after):

```yaml
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:17.5-bookworm
  bootstrap:
    recovery:
      source: postgres-backup
      # omit recoveryTarget for latest; or pin a moment:
      # recoveryTarget: { targetTime: "2026-06-18 01:55:00+02" }
  externalClusters:
    - name: postgres-backup
      barmanObjectStore:
        destinationPath: "https://<STORAGE_ACCOUNT>.blob.core.windows.net/postgres"
        azureCredentials:
          storageAccount: { name: azure-backup-creds, key: AZURE_STORAGE_ACCOUNT }
          storageKey:     { name: azure-backup-creds, key: AZURE_STORAGE_KEY }
```

> The `azure-backup-creds` Secret must exist in `postgresql` first — it arrives
> via `secrets-infrastructure` in Phase 2. Verify with
> `kubectl -n postgresql get secret azure-backup-creds`.

Watch the restore:

```bash
kubectl -n postgresql get cluster postgres -w
kubectl -n postgresql logs -l cnpg.io/cluster=postgres -c postgres -f
```

Once `phase: Cluster in healthy state`, restore the role/password alignment per
**§4.5** — either apply the backed-up app secrets (§5) *before* apps reconcile, or
`ALTER ROLE` each app role.

### Phase 4 — Restore generated secrets

```bash
az storage blob download --account-name <STORAGE_ACCOUNT> -c secrets \
  -n "<date>/prod-secrets.yaml.gpg" -f /tmp/s.gpg
gpg -d /tmp/s.gpg | kubectl apply -f -      # repeat per namespace
shred -u /tmp/s.gpg
```

Apply these **before** the app HelmReleases finish reconciling so the bootstrap
Jobs reuse the existing `postgres-<component>-app` passwords.

### Phase 5 — Reconcile and verify

```bash
flux reconcile source git flux-system
flux get kustomization        # all Ready=True
for env in dev qa uat prod; do kubectl -n app-$env get pods; done
```

Restore the `postgres` Cluster spec to its normal (non-recovery) form in git once
healthy, so future reconciles don't attempt to re-bootstrap. Commit + push.

### Phase 6 — DNS / ingress cutover

Point `*.example.com` / `*.kube.example.com` at the new cluster's ingress IP
(Traefik LoadBalancer). Until DNS propagates, the platform is up but unreachable
by name.

## 8. Standard operating procedures (routine)

| Cadence | Task | Command / check |
|---|---|---|
| **Continuous** | WAL archiving healthy | `kubectl -n postgresql get cluster postgres -o jsonpath='{.status.conditions}'` — `ContinuousArchiving=True` |
| **Daily** | Scheduled backup succeeded | `kubectl -n postgresql get backup` — latest `phase: completed` |
| **Daily** | Generated-secret blob uploaded | check `secrets/<today>/` in Azure |
| **Daily** | Velero backup succeeded | `velero backup get` |
| **Weekly** | GPG key still restorable | re-import from Key Vault on a scratch host, `sops -d` one file |
| **Monthly** | **Restore drill** (§9) | restore latest backup into a throwaway namespace/cluster |
| **Quarterly** | Full DR game-day | execute §7 end-to-end on a scratch cluster, time the RTO |
| **On change** | Re-export GPG key if rotated | §3 |
| **On new app** | Confirm its DB role + secret are covered by §5 dump | — |

### Monitoring / alerting to wire up

- Alert if `ContinuousArchiving` condition ≠ `True` for > 10 min (WAL not shipping → RPO blown).
- Alert if no `Backup` with `phase: completed` in the last 26 h.
- Alert on Azure container size anomalies (backups stopped, or runaway growth).
- The CNPG `PodMonitor` is already enabled (`pg-monitoring.yaml`) — add Prometheus
  rules for the above on top of it.

## 9. Restore drill (do this monthly — an untested backup is not a backup)

Validate the Postgres backup **without** touching production:

```bash
# Restore latest backup into a temporary, isolated cluster object
cat <<'YAML' | kubectl apply -f -
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: postgres-restore-test
  namespace: postgresql
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:17.5-bookworm
  storage: { size: 2Gi, storageClass: kubernetes }
  bootstrap:
    recovery: { source: postgres-backup }
  externalClusters:
    - name: postgres-backup
      barmanObjectStore:
        destinationPath: "https://<STORAGE_ACCOUNT>.blob.core.windows.net/postgres"
        azureCredentials:
          storageAccount: { name: azure-backup-creds, key: AZURE_STORAGE_ACCOUNT }
          storageKey:     { name: azure-backup-creds, key: AZURE_STORAGE_KEY }
YAML

# Verify it came up and has data
kubectl -n postgresql exec -it postgres-restore-test-1 -- \
  psql -U postgres -c '\l'                       # databases present?
kubectl -n postgresql exec -it postgres-restore-test-1 -- \
  psql -U postgres -d <appdb> -c 'SELECT count(*) FROM <key_table>;'

# Tear down
kubectl -n postgresql delete cluster postgres-restore-test
```

Record the drill result (date, backup age restored, row counts, time taken) in the
ops log. A drill that fails is a P1 — the DR plan is not real until the most recent
drill passed.

## 10. Pre-flight checklist (is DR actually in place?)

- [ ] GPG private key in Azure Key Vault **and** one offline location, re-import verified
- [ ] Azure storage account `<STORAGE_ACCOUNT>` created, GRS, lifecycle rules set
- [ ] `azure-backup-creds` Secret committed (SOPS-encrypted) and applied to `postgresql`
- [ ] `barmanObjectStore` added to `pg-cluster.yaml`, `ContinuousArchiving=True`
- [ ] `ScheduledBackup` running, latest backup `completed`
- [ ] Generated-secret nightly dump uploading (encrypted) to Azure
- [ ] Velero (or VM snapshot export) running for cluster/PV state incl. Harbor
- [ ] Bitbucket repo mirrored to a second remote (Bitbucket is the bootstrap source — a second mirror removes it as a single point of failure)
- [ ] Last monthly restore drill passed (date: ________)
- [ ] RTO measured in a game-day and meets the §1 target
